1. **以精品咖啡单店经营为核心**，不做通用餐饮 SaaS 的功能堆砌。
2. **H5 先行、小程序跟随**，前端采用一套代码双端编译（uni-app），后端 API 完全复用。
3. **首期做减法**：点单闭环 + 商家管理 + 基础统计为 P0；会员/储值/智能分析为后续迭代。
4. 冲突之处在「1.3 关键决策」中显式说明取舍理由。

### 1.3 关键决策（本文档的取舍）

| 决策点 | 来源分歧 | 本文档决策 | 理由 |
| --- | --- | --- | --- |
| 前端技术栈 | Codex 用 Vue3+Vite+Vant（H5/后台两套）；Gork/Gemini/DeepSeek 用 uni-app | **uni-app（Vue3 + TS + Pinia）一套代码双端编译** | 用户目标同时包含 H5 与微信小程序，避免二次重写 |
| 后端技术栈 | Gork 建议 Java/Node 二选一；其余均为 Node.js | **Node.js + TypeScript + Express + Prisma + MySQL 8** | 与多数文档一致、生态轻量、AI 辅助开发效率高；若技术人员更熟 Java，接口约定不变 |
| 会员/储值 | Codex 放 Phase 2；Gork 第一期不做；Gemini 纳入核心；DeepSeek 本期不含 | **P0 不含，P1 迭代** | 首期控制复杂度，先跑通点单闭环 |
| 退款 | DeepSeek 作为本期功能；其余未强调 | **P0 提供顾客申请 + 商家审核** | 精品咖啡客单价高，退款体验影响口碑，且实现成本低 |
| 支付 | H5 阶段各家均建议模拟支付 | **H5 提供模拟支付开关；小程序阶段接微信支付** | 域名备案未完成前无法使用微信 H5 支付，模拟支付保证流程可测 |
| 菜单规格模型 | 各家字段不同 | **统一规格组 JSON（杯型/温度/糖度/奶/浓度/加料），支持加价** | 中等复杂度，数据库灵活，避免过度建模 |
| 品牌色 | 多套相近色值 | **统一 Design Tokens（见 7.2）** | 视觉一致性优先 |

## 1. 项目概述

### 1.1 项目背景

一家非连锁精品咖啡店，个体户经营，桌位少于 20 张，高峰约 50 单/小时。目前点单依赖人工，存在以下问题：

- **顾客侧**：排队点单体验差、等待时间长、无法沉淀复购关系。
- **商家侧**：缺少经营数据、不知道商品表现、无会员体系。

店主已有：微信小程序认证资质（可能需续期）、一台初级云服务器、微信支付能力、云打印机、固定技术人员可后期维护。域名备案进行中。

### 1.2 项目目标与成功标准

目标：打造一套属于单店精品咖啡店自己的轻量数字经营系统，实现：

```
扫码点单 → 在线支付 → 订单制作 → 会员沉淀 → 经营分析
```

成功标准：

- H5 核心闭环（扫码 → 点单 → 支付 → 打印 → 后台管理）稳定可用。
- 一套代码同时产出 H5 与微信小程序，后端 API 完全复用。
- 自托管部署，首期投入可控（≤3000 元，不含已有服务器/打印机）。
- 视觉达到精品咖啡调性（自然、高级、温暖、克制），无廉价感。
- 店员可简单操作后台，技术人员可独立维护迭代。

### 1.4 范围界定

**本期（P0）做：**

- 顾客端：扫码进入（桌码/外带码）、菜单浏览、商品规格定制、购物车、下单、支付（H5 模拟/小程序微信支付）、订单状态、取餐码、退款申请。
- 商家端：登录鉴权、经营看板、订单工作台（接单/出餐/完成/退款审核）、商品与分类管理（含售罄）、桌台与二维码管理、基础统计、营业开关、打印机配置。

**本期（P0）明确不做：**

复杂营销活动、优惠券、分销、外卖平台对接、多门店、KDS 厨显、排队叫号、储值卡、会员积分体系。

**下一迭代（P1）做：**

简单会员（手机号绑定 + 消费记录）、储值与余额支付、数据导出 Excel、订单自动打印优化、语音提醒、基础满减优惠券。

**远期（P2）：**

AI 经营分析、销售预测、客户画像、菜单优化建议、个性化推荐。

## 2. 用户角色与权限

| 角色 | 说明 | 主要权限 |
| --- | --- | --- |
| 顾客（Customer） | 到店扫码或自取用户，无需注册登录 | 浏览菜单、下单支付、查看本人订单、申请退款、（P1）储值 |
| 店员/咖啡师（Staff） | 负责接单、制作、出餐 | 订单工作台、售罄/估清、简单统计 |

| 技术人员（运维） | 部署与维护 | 服务器、数据库、日志、备份 |

## 3. 核心业务流程

### 3.1 堂食扫码点单

```
顾客入座 → 扫描桌码（URL 携带 table_id）
→ 浏览菜单 → 选择规格（杯型/温度/奶/加料）
→ 加入购物车 → 提交订单（锁定桌号）
→ 支付（H5 模拟 / 微信支付）
→ 商家接单 → 制作 → 出餐（顾客端提示取餐）
→ 完成订单
```

### 3.2 外带/自取

```
扫描吧台外带码（无 table_id）→ 进入外带模式
→ 点单支付 → 生成取餐码 → 制作 → 叫号/通知取餐
```

### 3.3 退款流程

```
顾客在订单详情申请退款（选择原因）
→ 订单状态变为「退款中」
→ 商家在退款审核列表处理
→ 同意（退款） / 拒绝（恢复原状态，顾客可见原因）
```

## 4. 功能需求详述

### 4.1 顾客端（H5 / 小程序）

#### 4.1.1 扫码进入与桌位绑定

- 扫描桌码进入，URL 携带 `table_id`，自动进入堂食模式并锁定桌号，页面顶部显示「当前桌号：A08」。
- 扫描吧台外带码（无 `table_id`）默认外带模式，不绑定桌号。
- 支持手动切换桌号或切换「外带/不选座」。

#### 4.1.2 首页

- 目标：第一印象即「这是一家精品咖啡店」，而非外卖菜单。
- 结构：店铺 Logo/名称 → 品牌 Banner（店铺实拍图 + 品牌文案）→ 今日推荐 → 热门咖啡 → 分类入口 → 会员入口（P1 可见）。

#### 4.1.3 菜单与商品卡片

- 顶部横向分类栏：经典咖啡 / SOE 特调 / 手冲 / 茶饮 / 甜品 / 轻食（按店铺配置）。
- 商品网格（每行 2 个）或「左侧分类 + 右侧列表」。
- 商品卡片：图片（1:1）、名称 + 英文名、风味描述（如「茉莉花 / 柑橘 / 白桃」）、价格、产区/豆种与烘焙度轻标签、加号按钮。

#### 4.1.4 商品详情与规格定制

核心页面，规格以底部抽屉呈现：

| 规格组 | 选项示例 | 加价示例 |
| --- | --- | --- |
| 杯型 | 标准 / 大杯 | 大杯 +5 |
| 温度/冰度 | 热 / 少冰 / 正常冰 | — |
| 糖度 | 标准 / 少糖 / 无糖 | — |
| 奶类 | 全脂奶 / 燕麦奶 / 厚奶 | 燕麦奶 +3 |
| 浓度 | 标准 / 加浓 | 加浓 +3 |
| SOE 豆种 | 默认拼配 / 埃塞俄比亚 SOE | +4 |
| 加料 | 浓缩 / 糖浆 | 按配置 |

- 选择规格后**实时计算价格**。
- 支持备注输入（如「不要太烫」）。
- 底部操作：加入购物车 / 立即下单。
- 精品咖啡商品额外展示：产区/豆种、烘焙度、风味描述。

#### 4.1.5 购物车

- 底部常驻购物车条：数量、合计金额、去结算。
- 购物车页：商品、规格摘要、单价、数量增减、删除、整单备注、合计。
- 支持修改已加入商品的规格。

#### 4.1.6 确认订单

- 用餐方式：堂食（显示已绑定桌号，可修改）/ 外带（可填写取餐人手机号后四位，选填）。
- 商品明细、整单备注、合计金额（外带可配置包装费）。
- 提交订单 → 创建订单 → 进入支付。

#### 4.1.7 支付

- H5 阶段：模拟支付开关（测试环境一键标记已支付）；正式营业建议尽快切换微信支付。
- 小程序阶段：微信支付（复用已开通商户号）。
- P1：储值余额支付 + 余额不足时组合支付/跳转充值。

#### 4.1.8 订单状态与取餐通知

状态流转：

```
待支付 UNPAID → 已支付/待接单 PAID → 制作中 MAKING → 待取餐 READY → 已完成 COMPLETED
          ↘ 退款中 REFUNDING → 已退款 REFUNDED
          ↘ 已取消 CANCELLED
```

- 订单详情页展示**大字号取餐码**（如 S008）与节点式状态进度条。
- 出餐时顾客端提醒：
  - H5：页面轮询（约 10 秒）或 WebSocket，状态变更弹窗提示。
  - 小程序：微信订阅消息推送。

#### 4.1.9 我的订单

- 订单列表（按状态筛选）+ 订单详情。
- 支持「再来一单」。

#### 4.1.10 退款申请

- 已支付订单可申请退款，选择原因并提交。
- 展示退款状态：审核中 / 已同意 / 已拒绝。

#### 4.1.11 会员与储值（P1）

- 我的咖啡档案：头像、会员等级、累计消费、消费次数、余额、充值入口、消费记录。
- 定位是「咖啡档案」而非积分商城，保持品牌调性。

### 4.2 商家端

#### 4.2.1 登录鉴权

- 账号密码登录，JWT 会话，密码 bcrypt 加密。
- 仅授权店员可访问；管理员可管理员工账号。

#### 4.2.2 首页经营看板

- 今日实时营收、订单总数、待接单数量、客单价、新增会员（P1）。
- 新订单提醒：自动刷新 + 提示音（Web Audio）。

#### 4.2.3 订单工作台

- 按状态 Tab 分类：待接单 / 制作中 / 待取餐 / 已完成 / 退款中。
- 订单卡片：桌号或外带、商品摘要、总金额、下单时间、取餐码。
- 操作：接单（→ 制作中）、出餐（→ 待取餐，触发顾客端通知）、完成、取消、退款审核。
- 特殊定制要求（加浓、燕麦奶等）在商家端高亮显示，方便咖啡师一眼识别。

#### 4.2.4 商品与分类管理

- 分类增删改、排序。
- 商品增删改：名称、图片、价格、描述、规格组配置、产区/豆种/烘焙度/风味、上架/下架。
- 售罄（估清）快捷开关：咖啡师可在繁忙时一键标记某商品售罄。

#### 4.2.5 桌台与二维码

- 桌台列表（01–20 以内）、增删改、启用/停用。
- 为每桌生成带 `table_id` 参数的二维码图片，支持下载/批量打印。
- 生成通用「外带码」。

#### 4.2.6 数据统计

- 按日/周/月查看营收、订单量、客单价。
- 热销商品排行（按销量 / 金额）。
- 按小时时段销售曲线。
- 简单复购统计（按手机号 / openid 去重）。
- 图表：柱状图、折线图（轻量图表库即可）。

#### 4.2.7 系统设置

- 店铺设置：名称、Logo、营业时间、公告。
- 营业开关：开启/关闭接单。
- 堂食/自取开关、外带包装费配置。
- 退款设置：是否允许顾客发起退款。
- 打印机绑定与测试打印（对接飞鹅 / 易联云等云打印机，HTTP 推送）。

## 6. UI/UX 设计规范

### 6.1 设计原则

干净、克制、专业、温暖、留白、质感。参考 %Arabica、Blue Bottle、Manner、Seesaw 的精品咖啡体验。

禁止：大量红色按钮、促销标签、复杂弹窗、满屏优惠、夸张动效。

### 6.2 Design Tokens

```css
:root {
  /* 品牌色系 */
  --primary: #2F2A26;        /* 深咖啡黑：主按钮、标题、选中态 */
  --accent: #C4A484;         /* 暖咖/燕麦：标签、强调、风味高亮 */
  --bg: #F7F4F0;             /* 米白：全局背景 */
  --card-bg: #FFFFFF;        /* 卡片背景 */
  --text-main: #1F1B18;      /* 主文字 */
  --text-sub: #6B625B;       /* 次文字 */
  --divider: #E8E2DB;        /* 分割线 */
  --success: #3E7C59;
  --warning: #C77F3A;
  --danger: #B04A3A;

  /* 圆角与阴影 */
  --radius-sm: 8px;          /* 标签、小按钮 */
  --radius-card: 16px;       /* 商品卡片 */
  --radius-btn: 24px;        /* 胶囊按钮 */
  --shadow-card: 0 2px 8px rgba(0, 0, 0, 0.04);
}
```

### 6.3 字号规范

| 用途 | 字号 |
| --- | --- |
| 页面标题 | 24px bold |
| 分类标题 | 18px semibold |
| 商品名 | 16px medium |
| 价格 | 18px bold |
| 正文 | 14px |
| 辅助信息 | 12px |
| 按钮 | 15px |
| 取餐码 | 48px bold |

### 6.4 关键页面布局

- **顾客端首页**：顶部店铺名 → 分类横滑栏 → 商品网格（每行 2 个）→ 底部购物车条。
- **商品详情**：顶部大图 → 名称/描述/价格 → 规格组 → 备注 → 底部加购/立即下单。
- **订单确认**：堂食/外带切换 → 桌号 → 商品明细 → 备注 → 合计 → 提交按钮。
- **支付成功**：大号取餐码 → 状态提示 → 引导订阅通知 → 查看订单。
- **订单详情**：取餐码 + 节点式状态进度条 + 商品明细。
- **商家端**：顶部营收卡片 → 订单 Tab 分类 → 订单卡片列表 → 底部导航（订单/商品/桌台/统计/设置）；商家工作台可用暗色高对比模式（#121212 背景，定制需求高亮）。
- **空状态**：极简线条插画（咖啡杯/豆），避免卡通。

### 6.5 文案语气

专业克制。按钮示例：「加入购物车」「确认下单」「立即支付」。品牌文案示例：「一杯咖啡，连接慢生活」。

## 7. 系统架构与技术选型

### 7.1 演进架构

```
Phase 1（H5）                      Phase 2（微信小程序）
─────────────────                  ─────────────────
顾客端 uni-app → H5                顾客端 uni-app → 微信小程序
商家端 uni-app H5（PC 适配）          商家端复用
        │                                  │
        └────────── REST API ──────────────┘
                        │
                 Node.js + Express
                        │
              MySQL 8（数据完全一致）
                        │
         Nginx + PM2（云服务器自托管）
```

### 7.2 前端（uni-app）

- uni-app（Vue3 + TypeScript）+ Pinia + 轻量请求封装（axios）。
- 一套代码编译 H5 与微信小程序；微信登录、微信支付、订阅消息通过条件编译与平台适配层实现。
- 规格选择、购物车、订单等核心页面不依赖平台 API，双端复用。

### 7.3 后端

- Node.js + TypeScript + Express（或 Fastify）。
- Prisma ORM + MySQL 8。
- JWT 鉴权（商家端）、bcrypt 密码加密。
- 模拟支付开关（环境变量控制）；预留微信支付下单/回调接口。
- qrcode 库生成桌码；云打印机通过 HTTP 推送对接。

### 7.4 部署

- 商品图片暂存服务器本地，预留云存储迁移。

`id, username(unique), password_hash, role(STAFF/MANAGER), created_at`

## 9. API 接口设计（概要）

### 9.1 通用约定

- 响应格式：`{ "code": 0, "data": ..., "msg": "success" }`
- 错误码：0 成功 / 1 参数错误 / 401 未授权 / 403 无权限 / 500 服务器错误。
- 商家端接口带 `Authorization: Bearer <JWT>`。

### 9.2 顾客端接口（无需登录）

| GET | `/api/tables` | 桌台列表（手动选桌用） |

| POST | `/api/orders/:id/mock-pay` | 模拟支付（H5 测试） |
| POST | `/api/orders/:id/pay` | 微信支付下单（小程序） |
| POST | `/api/payment/callback` | 微信支付回调 |

| POST | `/api/auth/mock-login` | H5 匿名用户标识（生成 user_id） |

## 11. 开发计划（Plan）

### 11.1 阶段总览

| 阶段 | 内容 | 预估 | 产出 |
| --- | --- | --- | --- |
| Phase 0 | 项目初始化与设计落地 | 0.5–1 天 | 仓库、环境变量、Prisma schema、seed、Design Tokens |
| Phase 1 | 后端核心 API | 2–3 天 | 顾客端 + 商家端全部接口可调用 |
| Phase 2 | 顾客端 H5 | 3–4 天 | 首页→点单→支付→订单全流程可用 |
| Phase 3 | 商家后台 | 2–3 天 | 看板、订单、商品、桌台、统计、设置 |
| Phase 4 | 联调打磨 | 1–2 天 | 状态流转、轮询通知、UI 走查、性能 |
| Phase 5 | 部署上线 | 0.5–1 天 | 服务器部署、桌码打印、店员培训 |
| Phase 6 | 微信小程序适配 | 3–5 天 | 小程序编译、登录、支付、订阅消息、真机测试 |

> 合计：MVP（Phase 0–5）约 2–3 周；小程序适配另需 3–5 天（含微信审核提交）。

### 11.2 Phase 0 · 初始化（0.5–1 天）

- 初始化 `server/`（Node.js + TS + Express + Prisma + ESLint + dotenv）。
- 初始化 `web/`（uni-app Vue3 + TS + Pinia + 请求封装）。
- 编写 Prisma schema 与 seed（分类、示例精品咖啡商品、默认管理员、桌台）。
- 配置 Design Tokens 与公共组件骨架。

### 11.3 Phase 1 · 后端核心（2–3 天）

- 商家登录与 JWT 鉴权。
- 分类/商品/桌台 CRUD + 售罄开关。
- 创建订单（含取餐码生成）、模拟支付、微信支付预留接口。
- 订单状态流转与退款审核。
- 统计接口（今日看板、日/周/月、热销、时段）。
- 店铺设置与打印机接口。

### 11.4 Phase 2 · 顾客端 H5（3–4 天）

- 扫码进入（解析 `table_id`）与堂食/外带模式。
- 首页、菜单、商品详情（规格抽屉 + 实时计价）。
- 购物车（底部常驻条、增删改、备注）。
- 确认订单、模拟支付、支付成功（取餐码大图）。
- 订单列表/详情（状态进度 + 轮询）、退款申请。

### 11.5 Phase 3 · 商家后台（2–3 天）

- 登录页与看板（今日营收/订单/待接单）。
- 订单工作台（状态 Tab、接单/出餐/完成、新单提示音）。
- 商品与分类管理、售罄开关。
- 桌台管理 + 二维码生成/下载。
- 统计页（图表）与系统设置。

### 11.6 Phase 4 · 联调打磨（1–2 天）

- 全流程回归：扫码 → 点单 → 支付 → 接单 → 出餐 → 完成 → 退款。
- 移动端适配与性能（菜单 <2s、提交 <1s）。
- 空状态、异常态（售罄、停业、支付失败）处理。

### 11.7 Phase 5 · 部署上线（0.5–1 天）

- 服务器环境（Nginx + PM2 + MySQL + 备份脚本）。
- 域名/HTTPS（备案完成后）。
- 生成并打印桌码、外带码；店员培训与操作手册。

### 11.8 Phase 6 · 微信小程序适配（3–5 天）

- uni-app 编译小程序 + 微信开发者工具联调。
- 微信授权登录（openid 绑定）、微信支付、订阅消息。
- 合法域名配置、隐私协议、提审发布。

### 11.9 验收标准（MVP）

- 顾客端：扫码进入、浏览、规格选择、加购、下单、支付、查看订单、退款申请全部可用。
- 商家端：接单、制作、出餐、完成、退款审核、商品/桌台管理、统计可用。
- 打印机：支付成功后自动打印小票（若打印机型号已确认）。
- 双端：同一份代码可编译 H5 与微信小程序，核心业务逻辑一致。

## 14. 风险与假设

- 域名备案完成前，H5 用 IP/临时域名测试，HTTPS 受限；建议优先推进备案。
- 微信 H5 支付需额外申请权限；若来不及，先模拟支付 + 小程序支付兜底。
- H5 无法像小程序一样推送服务通知，依赖轮询，体验略差；可引导顾客保留页面。
- 打印机需支持云 API 推送（飞鹅/易联云），型号确认后接入。
- 支付、订单数据需定期备份；商户密码加密存储。
- 高峰并发（50 单/小时）按现有初级服务器需做好索引与缓存，必要时升级配置。

## 15. 待确认事项

进入开发前需要确认以下事项：

1. **技术栈**：确认前端采用 uni-app（一套代码双端）、后端 Node.js + Prisma + MySQL；若技术人员更熟悉 Java 需提前说明。

8. **服务器**：现有云服务器配置、操作系统、MySQL 是否已安装、域名备案进度。
