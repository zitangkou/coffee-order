# Coffee OS 电脑端管理后台规划

## 1. 目标与边界

电脑端管理后台面向店长、店员、运营和财务人员，重点解决高频订单操作、商品与桌台维护、经营分析、权限审计和后续营销扩展。

当前 `web/src/pages_admin` 继续作为首发阶段的可用后台；中长期新建独立 `admin-web`，避免在 uni-app H5 页面中持续堆叠复杂桌面交互。微信小程序顾客端、电脑管理端和后端 API 分离构建，但继续复用同一套业务服务和数据库。

## 2. 推荐架构

```text
微信小程序顾客端 ── /api/* ─────────────┐
                                         ├── Node.js API ── MySQL
电脑管理端 admin.nagacoffee.site ── /api/admin/*
                                         ├── 微信支付/订阅消息
                                         ├── 打印服务
                                         └── 备份、监控、定时任务
```

- 顾客端：保留现有 `web` 微信小程序构建。
- 电脑端：新增 `admin-web`，建议使用 Vue 3、Vite、TypeScript、Pinia、Vue Router、Element Plus、ECharts。
- 后端：保留现有 `server`，逐步扩展 `/api/admin`。
- 部署：管理端静态资源独立容器，建议使用 `https://admin.nagacoffee.site`；首版独立后台完成前，现有管理端仍使用 `https://nagacoffee.site/#/pages_admin/login/index`。
- 服务器：单店首发阶段 4 核 4G、40G 可承载 MySQL、API 和两个静态前端；图片与备份应逐步迁移至 COS，避免长期占用系统盘。

## 3. 桌面布局与信息架构

采用左侧导航、顶部状态栏和中部工作区的桌面布局，主要适配 1366×768、1440×900、1920×1080。

一级菜单：

1. 经营看板
2. 订单中心
3. 商品中心
4. 桌台与取餐码
5. 会员管理
6. 营销运营
7. 数据分析
8. 门店设置
9. 员工与权限
10. 操作日志
11. 系统状态

通用交互要求：

- 列表筛选条件保留、分页、批量操作和自定义列。
- 详情优先使用右侧抽屉，编辑使用抽屉或弹窗，减少频繁整页跳转。
- 高风险操作二次确认，成功后明确反馈，失败时保留输入和筛选状态。
- 支持键盘操作、清晰焦点、表单标签和足够的颜色对比度。

## 4. 功能规划

### 4.1 经营看板

- 今日营业额、实收、订单数、客单价、退款金额和退款率。
- 待接单、制作中、待取餐数量及超时提醒。
- 小时订单趋势、堂食/外带占比、热销商品和品类排行。
- 昨日、上周同期对比。
- 支持今天、昨天、近 7 天、近 30 天、本月和自定义日期。
- 展示支付异常、退款失败、打印机离线、备份过期、磁盘容量等异常。

### 4.2 订单中心

- 表格字段包含订单号、取餐码、时间、类型、桌号、商品摘要、金额、支付/制作/退款状态和操作人。
- 支持订单号、取餐码、手机号后四位、日期、桌台和状态筛选。
- 支持接单、出餐、完成、退款审核、退款同步和重新打印。
- 详情展示订单状态时间线、支付记录、退款记录和后台操作记录。
- 首期继续 10 秒轮询；订单规模增加后升级 SSE 或 WebSocket。

### 4.3 商品中心

- 商品、分类、规格、图片和售罄状态分别管理。
- 批量上下架、批量分类、拖拽排序、价格和图片维护。
- 支持单选、多选、必选、默认选项和附加价格。
- 保存前校验必选规格、有效选项、价格和上下架状态。
- 支持临时售罄及自动恢复时间。

### 4.4 桌台与取餐码

- 新增、编辑、启用、停用桌台。
- 批量生成、预览、下载和 A4 排版打印桌台码。
- 单独生成外带码，显示二维码生成状态和失败原因。
- 有历史订单的桌台不物理删除，改为停用。

### 4.5 会员管理

- 首期提供用户查询、累计消费、订单数、客单价、最近消费、退款次数、等级和最近订单。
- 手机号、OpenID 等敏感字段默认脱敏，查看操作进入审计日志。
- 后续扩展会员标签、消费偏好、活跃/沉睡用户、优惠券和风险标记。

### 4.6 营销运营

在订单和支付稳定后分期增加优惠券、满减、套餐、新客优惠、会员日、首页推荐位、公告和活动效果统计。优惠计算和适用规则必须由后端校验。

## 5. 数据指标口径

| 指标 | 统一口径 |
| --- | --- |
| 营业额 | 成功支付金额 |
| 实收金额 | 成功支付金额减成功退款金额 |
| 订单数 | 成功支付订单数 |
| 客单价 | 成功支付金额 ÷ 成功支付订单数 |
| 退款率 | 成功退款订单数 ÷ 成功支付订单数 |
| 商品销量 | 成功支付且未全额退款的商品数量 |
| 制作时长 | 接单时间至出餐时间 |
| 完成时长 | 支付时间至订单完成时间 |

后续建议增加 `order_status_logs`、`daily_shop_stats`、`daily_product_stats`、`member_tags` 和业务备注表。早期直接查询业务表，数据量增加后使用每日汇总表和定时聚合任务。

## 6. 权限与安全

角色建议包括店长、店员、财务、运营和只读人员，逐步从 `MANAGER/STAFF` 升级为操作级 RBAC：

- `order.read`、`order.status.update`
- `refund.approve`
- `product.edit`、`product.delete`
- `stats.export`
- `admin.manage`

安全要求：

- 独立 HTTPS 子域名、登录限流、失败次数限制和长时间无操作自动退出。
- 密码或角色变更后旧令牌立即失效。
- 敏感字段脱敏，退款、导出和管理员操作记录审计日志。
- CSV 防公式注入，高风险操作二次确认。
- 微信和支付密钥仅由后端受控配置读取，不进入管理端源码、构建产物或日志。
- 后续可增加微信扫码登录或 TOTP 二次验证。

## 7. 实施排期

### 第一阶段：桌面基础版（进行中）

- 新建 `admin-web`、登录、路由权限和桌面布局。
- 经营看板基础版、订单中心、商品和桌台管理。
- Docker 构建与子域名部署。

### 第二阶段：操作效率（3–5 天）

- 订单详情与时间线、批量商品操作、图片维护。
- 桌台码批量下载/打印、导出中心、操作日志和系统状态。

### 第三阶段：运营统计（5–7 天）

- 营业、商品、时段、退款、会员和制作效率分析。
- 每日统计汇总、异常提醒和会员管理。

### 第四阶段：营销能力（按经营需要）

- 优惠券、满减、套餐、用户标签、活动分析和消息公告。
- 数据模型预留 `storeId`，实际有多门店需求后再启用多门店能力。

## 8. 第一版验收标准

- 管理员可稳定登录、退出，店员与店长权限严格隔离。
- 新订单 10 秒内展示，接单、出餐、完成和退款流程闭环。
- 商品、规格、售罄和桌台可维护。
- 核心统计与数据库订单口径一致。
- 1366px 以上屏幕无明显布局错位。
- 高风险操作有确认和审计记录。
- 管理端构建产物不含任何微信或支付密钥。
- Docker 可独立构建部署，小程序产物不包含电脑后台代码。

## 9. 当前实施决策

独立 `admin-web` 已开始建设。现有 H5 商家后台继续作为线上回退入口，电脑端在核心功能验收前仅绑定服务器本机端口；验收通过、管理子域名 DNS/HTTPS 和 CORS 配置完成后，再切换 `admin.nagacoffee.site`。
