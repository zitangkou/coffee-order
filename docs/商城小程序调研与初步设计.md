| # | v0.1 | v0.2 为什么改 |
|---|---|---|
| 1 | 商城内再做一套独立 4 Tab（首页/分类/购物车/我的商城） | 微信小程序全局只有一套 `tabBar`；5–10 个 SKU 不值得再造一套导航。学有赞咖啡模板：首页金刚区放「快递商城」，页面走分包，订单/地址并进现有「我的」 |

| 5 | 凑单免邮放二期 | 京东式「还差 ¥X 包邮」实现成本极低、对挂耳/杯子凑单直接有效，**拉进一期购物车/结算条** |
| 6 | 商品详情只写风味星级 | 精品豆零售标配「烘焙日期 / 最佳赏味」。SKU 增加 `roastDate`（可空），详情页展示 |
| 7 | 点单成功弹窗推荐豆子 | 保留，并加 `Product.linkedMallProductId`，把「今天这杯的豆子」做成数据关联而不是文案硬编码 |
| 8 | 地址完全自建表单 | 优先 `wx.chooseAddress` 拉微信地址簿，再落库；减少填写摩擦 |
| 9 | 客服未写 | 商详/订单详情放微信「联系客服」按钮（`button open-type="contact"`），单店客诉走店主微信，不自建工单 |

## 0. 一句话结论

**不另起独立小程序。** 在现有点单小程序里加一个轻量「货架」分包：复用微信登录、JSAPI 支付、退款与审计；新增零售商品（SKU 库存）+ 服务端购物车 + 地址 + 快递/到店自提。一期只做「陈列—加购—下单—支付—发货或核销—确认收货—售后」闭环，并**必须**接入微信发货信息管理（否则实物货款可能无法结算）。营销、直播、积分商城、物流轨迹插件全部二期。

## 1. 产品定位与目标

### 1.1 定位

在现有「到店扫码点单」上，加一个**面向私域熟客的轻量零售货架**，把到店喝过的风味（挂耳、咖啡豆、冻干、礼盒）和品牌周边（杯子、香囊）卖回家。

核心场景：

> 顾客到店喝了一杯 → 觉得不错 → 在「商城」把同款豆子 200g / 挂耳快递回家，或下次到店自提一只杯子。

不是公域比价货架，也不是三顿半/永璞那种「内容 + 积分游戏 + 社群裂变」的 DTC 品牌操作系统。

### 1.2 目标用户

- **到店老客**（已有 openid / 会员档案）：复购豆子、挂耳
- **熟客自提**：到店顺手带走已下单零售品
- **礼赠**（节令礼盒）：二期再加重包装与贺卡

明确不是：泛公域流量客、价格敏感比价用户。因此不碰拼多多/淘宝开店，也不做砍价拼团。

### 1.3 MVP 做什么 / 不做什么

| 维度 | ✅ 一期（MVP）做 | ⏭️ 二期再做 | ❌ 不做 |
|---|---|---|---|
| 商品 | 挂耳 / 豆子 / 冻干 / 礼盒 / 杯子 / 香囊；SKU=售卖规格（克重/包数）；豆子研磨为下单选项 | 节令礼盒、赠品组货、加价购、烘焙批次高级管理 | 直播带货、内容种草、小岛游戏 |
| 购物车 | 服务端购物车，仅商城商品；底部「还差 ¥X 包邮」 | 失效商品折叠优化、购物车推荐 | 与现制饮品车合并结算 |
| 履约 | 全国快递 + 门店自提；发货后写入微信发货信息管理 | 同城配送、按重量续重、电子面单打单 | 达达 / 闪送 |
| 订单 | 待付款→待发货/待自提→待收货→完成；微信确认收货组件 | 发票、拆单发货 | 预售 / 拼团 |
| 支付 | 复用微信 JSAPI；支付成功后按履约类型上传发货信息（自提可立即报「用户自提」） | 余额抵扣、组合支付 | 货到付款 |
| 售后 | 仅退款 + 退货退款（复用 Refund）；页面写死食品拆封规则 | 换货、上门取件、运费险、退货组件 | 平台介入式工单 |
| 会员 | 同一 User；商城实付计入现有成长档案 | 积分商城、积分抵现、复购券 | PLUS / 付费会员、企微裂变矩阵 |
| 营销 | 满 X 包邮（固定运费否则）；后台手动改价 | 复用 Promotion 满减/新客券 | 拼团砍价、签到游戏 |

## 2. 竞品调研（v0.2 扩围）

调研分四层，避免只抄连锁茶饮或只抄综合电商。

- 【事实】= 有公开文档 / 官方产品说明 / 公开案例
- 【判断】= 结合单店约束的推断，不作为唯一硬依据

### 2.1 综合电商与微信官方能力

| 产品 / 能力 | 对本店有用的部分 | 明确不学 |
|---|---|---|
| **微信小店** | 履约三件套：快递 / 同城 / 自提；售后类型仅退款、退货退款、换货、补寄；商家处理时效 24–36h，超时默认同意 | 达人分佣、短视频货架、电子面单强制（自营小程序不走小店发货 API） |
| **小程序发货信息管理**（官方，实物类必接） | 发货后 `upload_shipping_info`；`logistics_type`：1 快递 / 2 同城 / 3 虚拟 / **4 用户自提**；用户侧确认收货组件；超时自动确认后才结算资金 | 把「物流轨迹页」当成一期自研功能——平台发货消息已经把物流推给用户 |
| **wx.chooseAddress** | 调起微信地址簿，减少自建省市区选择器 | 完全依赖微信、不落库（用户换机/拒权后无默认地址） |
| **京东** | 购物车底栏「再买 ¥X 免运费」；商详底部固定「加购 / 立即买」 | PLUS、跨店凑单、自营物流时效承诺 |
| **淘宝** | 失效商品折叠；7 天无理由分区（非食品） | 跨店满减、红包体系 |
| **拼多多** | 状态机把「待分享成团」独立出来——提醒我们**异步状态不要塞进普通待发货** | 拼团、砍价、平台介入 |
| **抖音商城** | 内容卡带货（二期才可能用视频号） | 公域投流作为一期获客 |

**关键事实：**

- 【事实】微信《商家自营类小程序运营规范》：特定类型小程序须完成发货信息录入及确认收货后，平台才做资金结算。未上传发货信息时货款处于冻结。
- 【事实】发货信息录入支持自提（`logistics_type=4`）。门店自提**不是**「可以不报发货」。
- 【事实】确认收货可调 `wx.openBusinessView`（`businessType=weappOrderConfirm`），服务端须再查一次发货状态，不能只信前端回调。
- 【判断】一期不接快递 100 / 快递鸟：微信发货消息已覆盖「用户知道货在哪」；自研轨迹页投入产出比低。

### 2.2 连锁现制：点单之外怎么卖货

| 品牌 | 形态 | 点单与零售 | 启发 | 不学 |
|---|---|---|---|---|
| **星巴克中国** | 同一 App/小程序：啡快、专星送、**咖啡生活馆**（杯具/豆子送到家） | 【事实】星享俱乐部按人绑定；门店 / App / 小程序 / 咖啡生活馆 / 指定天猫渠道消费可积成长值；啡快与生活馆都可积星（除外商品除外） | **一个账户跨现制+零售**；履约分流、购物车不混 | 星礼卡、多人拼单、星动市集兑换 |
| **瑞幸** | 点单 App 内「潮品/商城」；联名周边常做成**兑换券进钱包、到店核销** | 同账户；重货走京东/天猫/抖音旗舰 | 「轻周边」可以是券而不是快递 | 独立即享旗舰店、价格战 |
| **喜茶 GO** | 点单主程序 + **独立**「喜茶百货」 | 账户在 GO；百货独立 | 点单主路径保持轻 | **单店流量养不起第二个小程序** |
| **霸王茶姬** | 点单内积分商城兑茶包/周边 | 点单攒分 → 兑零售 | 积分适合二期反哺频次 | 一期就做积分商城 |
| **库迪** | 小程序偏点单；零售主战场在天猫/直播 | 小程序内少见结构化货架 | 「挂耳+赠品杯」组货可二期借 | 直播价、补贴 |

### 2.3 咖啡零售 DTC 与精品店（v0.1 弱项，本版补齐）

这类才是「卖豆子/挂耳」的直接同行，但规模和打法与单店不同。

| 品牌 | 【事实】公开打法 | 对单店 | 不学 |
|---|---|---|---|
| **永璞「永璞小岛」** | 小程序=商城+会员中心；「岛民」等级；积分来自消费/签到/包装回收；石端正 IP；公众号+企微+社群矩阵 | 品牌叙事可以很轻地用在商详（产地故事、冲煮），**不要**做成游戏岛 | 小游戏、签到积分、企微 200 群 |
| **三顿半** | 公域种草 → 有赞微商城沉淀；「返航计划」包装回收换积分 | 包装/礼盒里放一张「回店自提或再买豆子」卡片，比做回收物流现实 | 估值级内容投放、KOC 矩阵 |
| **隅田川** | 「隅田川鲜咖啡」小程序；入会送券；小程序触点导企微社群；私域复购极高（公开运营稿） | 一期在商详放客服即可；社群放二期、且只服务到店熟客 | 把小程序当拉群漏斗 |
| **Manner** | 小程序主战场是**到店点单**；豆子/挂耳更多走门店与公域电商；社群只从线下扫码进 | 【判断】精品店小程序应**点单优先、零售克制**，与 v0.1「不拆百货小程序」一致 | 把零售做成主 Tab 压过点单 |
| **Seesaw 等精品** | 豆子常用动物名 + 酸/苦星级；规格 250g/500g、挂耳按盒 | 商详卖风味与冲煮，不卖参数表 | 过度设计风味宇宙 |
| **有赞门店（咖啡/烘焙模板）** | 【事实】首页「客户资产」可放 2–5 个入口：堂食点单、门店自提、快递商城、会员、积分商城；点单与快递是**同一小程序不同页面**，订单履约字段不同 | **这是单店最可执行的 IA**：入口在首页，不造第二套 Tab | 付费 SaaS 营销插件一把梭 |

单店对标应是：**星巴克的账户打通 + 有赞的入口克制 + Manner 的点单优先 + 微信官方的发货结算**；不是永璞小岛，也不是喜茶百货。

### 2.4 对本项目的设计原则（从 10 条收敛为「做 / 不做」）

**做：**

1. 一个小程序、点单主路径不动；商城是分包页面，入口在首页金刚区 + 支付成功推荐 +「我的」。
2. 会员按人打通：同一 `User`，商城实付计入现有咖啡档案成长（积分抵现仍二期）。
3. 购物车按履约物理隔离：现制 Pinia 本地车 vs 商城服务端车，**禁止合并结算**。
4. 履约只开快递 + 门店自提；自提核销复用 `pickupNo`，但**订单状态不要复用堂食 READY**。
5. 商详学精品店：产区、烘焙、酸/苦、风味、冲煮、烘焙日期；底栏固定加购/立即买；食品售后一句话钉在底部。
6. SKU 只表达「卖什么规格」；研磨是订单项备注。
7. 运费：满 X 包邮，否则固定运费；购物车/结算实时显示差额。
8. 售后规则写死：食品未拆封可退、拆封不退；杯具 7 天无理由；破损/错发包退。商家 24–36h 处理，后台待办。
9. 「这杯的豆子」用 `Product.linkedMallProductId` 驱动支付成功弹窗，而不是每次手写文案。
10. 实物订单走微信发货信息管理 + 确认收货组件，保证结算。

**不做（包括优秀同行在做、但单店一期不该做的）：**

- 独立百货小程序、积分游戏岛、签到、企微裂变、直播
- 商城独立 4 Tab、信息流首页
- 研磨度拆 SKU 库存
- 自研物流轨迹（一期）
- 现制与零售混在一个购物车

## 3. 信息架构与页面

### 3.1 入口（克制，对齐有赞「业务入口」而不是第二套 App）

现有顾客端没有原生 `tabBar`（见 `web/src/pages.json`），首页自定义导航。**不要**为商城新增全局 4 Tab。

推荐入口：

1. **首页金刚区**：「☕ 带回家」（文案可改）→ 商城首页
2. **「我的 / 咖啡档案」**：商城订单、收货地址
3. **点单支付成功页**：若当前饮品绑定了零售商品，弹「今天这杯的豆子，200g 可寄到家」

商城内用**页内顶栏或底栏伪导航**即可：货架 / 购物车（角标） / 订单。不要和点单页抢主路径。

### 3.2 页面清单（MVP，比 v0.1 少 1 个独立分类 Tab）

| # | 页面 | 路径（`web/src/pages/mall/`，`subPackages`） | 说明 |
|---|---|---|---|
| 1 | 商城首页 | `mall/index` | 1 张 Banner + 分类胶囊 + 商品双列；分类少时**不单独做分类页**，胶囊锚点过滤即可 |
| 2 | 商品详情 | `mall/product` | 图集、价格、SKU（克重/包数）、研磨选项（若开启）、风味/冲煮/烘焙日、售后一行、底栏加购/立即买、分享给好友、联系客服 |
| 3 | 购物车 | `mall/cart` | 服务端；勾选/改数/失效置灰；合计 + 包邮差额 |
| 4 | 确认订单 | `mall/checkout` | 快递：地址（微信地址簿 + 地址簿）；自提：门店信息；运费；备注；提交 |
| 5 | 地址编辑 | `mall/address-edit` | 可从 `wx.chooseAddress` 预填；列表可并进「我的」减少一页 |
| 6 | 商城订单列表 | `mall/orders` | Tab：待付款 / 待发货 / 待收货 / 待自提 / 售后 |
| 7 | 订单详情 | `mall/order-detail` | 快递：运单号+复制；自提：自提码；确认收货调微信组件；售后入口 |
| 8 | 申请售后 | `mall/refund-apply` | 仅退款 / 退货退款；原因；凭证图二期 |

分类独立页（v0.1 的 `mall/category`）降为：SKU 超过约 30 个或分类超过 6 个再拆。一期 5–10 SKU 放首页足够。

支付结果页继续复用 `pages/order/result`，按 `bizType` 切换文案（取餐码 vs 待发货/自提码）。

## 4. 核心业务流程

### 4.1 主流程

```
[首页「带回家」/ 支付成功推荐]
  → [商城首页] 选品
  → [商详] 选 SKU（克重）[+ 研磨]
  → 加购（CartItem 落库）或立即买
  → [购物车] 勾选 → 结算（展示包邮差额）
  → [确认订单] 快递地址 / 门店自提 → 提交
  → Mall 订单 UNPAID → 微信 JSAPI
  → 支付成功 PAID：扣库存、记支付
       ├─ 快递：待发货；后台填承运商+运单号 → SHIPPED
       │     同时 upload_shipping_info (logistics_type=1)
       │     → 用户微信确认收货（或平台到期自动确认）→ COMPLETED
       └─ 自提：生成自提码 → AWAITING_PICKUP
             同时 upload_shipping_info (logistics_type=4)
             → 到店核销 → COMPLETED
  → 售后：未发货仅退款；已发货退货退款（现有 Refund + 资金原路退）
```

### 4.2 订单状态机（与堂食隔离）

现有堂食：`UNPAID → PAID → MAKING → READY → COMPLETED`（另有退款/取消）。

商城**不要进入 MAKING/READY**：

```
UNPAID
  ├─ 取消 / 超时 → CANCELLED（释放预占库存）
  └─ 支付成功 → PAID
        ├─ SHIPPING：PAID → SHIPPED → COMPLETED
        └─ PICKUP：  PAID → AWAITING_PICKUP → COMPLETED
        └─ 售后中 → REFUNDING → REFUNDED / 拒绝后回到原状态
```

商家后台订单工作台默认仍只看堂食；商城订单进独立「商城发货」列表，避免和出餐队列混在一起。

状态变化继续写 `OrderStatusLog`。

### 4.3 售后规则（一期）

| 商品类型 | 仅退款（未发货/漏发） | 退货退款（已发货） | 换货 |
|---|---|---|---|
| 挂耳 / 豆子 / 冻干 | ✅ | ✅ 未拆封；**拆封不退**（商详+售后页明示） | ❌ 二期 |
| 礼盒 | ✅ | ✅ 未拆封 | ❌ |
| 杯子 / 香囊 | ✅ | ✅ 7 天无理由（质量问题除外期限） | ❌ |

商家处理：后台待办，目标 24–36h 内同意或拒绝（对齐小店习惯，自营小程序没有「超时系统自动同意」，要用待办+订阅/看板补上）。

退货物流：一期让用户自行寄回并**填退货单号**（字段加在 Refund 或订单备注）；上门取件/退货组件二期。

### 4.4 库存

- SKU 库存；下单 **UNPAID 预占**，支付成功确认扣减，取消/超时/退款回补
- 预占超时与现有 `ORDER_TIMEOUT_MINUTES` 对齐（默认 15 分钟）
- 研磨不减库存

## 5. 数据模型（相对现有模型的增量）

现有 `Product` 是现制饮品（规格组、无 SKU 库存、单价格），**不直接当零售商品**。现有 `Order` 偏堂食，采用 **Order 扩展字段 + MallOrderItem**，以复用支付、退款、幂等、审计。

现有 `OrderItem.productId` 外键指向堂食 `Product`，商城行必须用独立 `MallOrderItem`，不能塞进 `OrderItem`。

## 6. 与 coffee-order 的集成

### 6.1 账号

- 继续 `POST /customer/auth/wx-login`，同一 JWT、`requireUser`
- 「我的」按 `bizType` 分开展现制 / 商城订单，避免一个列表里取餐码和运单号混排

### 6.2 支付与发货结算（一期硬依赖）

- 下单支付复用现有统一下单 / 回调 / 查单 / 关单 / 原路退款
- 商城 `body` 标明商品名；`attach` 带 `bizType=MALL`
- **支付成功之后：**
  - 自提：即可调用发货信息管理，`logistics_type=4`
  - 快递：后台点发货时调用，`logistics_type=1`，带承运商编码与运单号
- 用户确认收货：拉起微信确认收货组件，服务端 `get_order` 复核后再把本地状态打成 COMPLETED
- 平台自动确认收货事件 `trade_manage_order_settlement`：本地应对齐，避免用户未点、资金已结算但订单仍待收货

**上线前 readiness（只记状态，不记配置值）：**

1. 微信支付商户号经营类目是否覆盖预包装食品 / 咖啡豆 / 实物周边
2. 小程序类目与食品经营 / 预包装食品资质
3. 小程序是否已开通发货信息管理、商户号是否完成交易结算管理确认
4. 堂食现制订单若被平台识别为实物交易，需确认现制走「无需物流/虚拟或到店自取」报备策略，**避免把每杯拿铁也当成待发快递**（这是把商城接进同一小程序后的新风险）

### 6.3 后端路由（`/mall` 前缀）

顾客端：分类与商品、购物车、地址、下单（服务端重计价+运费+预占）、取消、我的订单、详情、申请售后、（服务端）标记微信发货已上传。

管理端：商品/SKU/库存、运费设置、发货（写运单号并调微信）、自提核销、售后处理。RBAC 与 AuditLog 复用。店员可核销自提；发货/退款建议店长。

### 6.4 前端

- uni-app 分包 `mall`
- `stores/mallCart.ts` 与现有 `cart.ts` 隔离
- `api/mall.ts` 复用请求封装
- 地址：优先 `wx.chooseAddress`（需在小程序后台申请接口权限并在 `manifest`/`app.json` 声明）
- 商详 `open-type="contact"`、`button open-type="share"`
- admin-web 增加「商城」菜单：商品、发货、售后、运费；**不要**塞进现有出餐工作台

### 6.5 部署

- 同一套 Docker；Prisma 双 schema 增量 migration
- 图片走现有 uploads，注意主包体积：商城页全部分包

## 8. 风险与待决

| # | 项 | 影响 | 处理 |
|---|---|---|---|
| 1 | 支付类目是否覆盖实物 | 无法收款 | 上线前微信支付后台确认 |
| 2 | 食品类目资质 | 无法上架豆子/挂耳 | 预包装食品备案 / 食品经营许可 |
| 3 | **发货信息管理未接入** | 货款冻结 | 一期必接；自提也要报 `logistics_type=4` |
| 4 | **现制订单被当成实物待发货** | 每杯咖啡都要「发货」才能结算 | 与微信侧确认交易类型；现制保持到店履约上报策略 |
| 5 | 运费 vs 客单价 | 单袋豆子可能不够包邮 | 默认满 99 / 否则 6 元，上线后按真实重量调整 |
| 6 | 两套购物车 | 用户混淆 | UI 分流；点单页不出现商城车 |
| 7 | 主包体积 | 超 2MB | 商城全部分包 |
| 8 | 食品拆封争议 | 客诉 | 商详固定文案 + 订单快照 |
| 9 | 堂食工作台被商城单污染 | 出餐效率 | 独立列表 + 状态枚举隔离 |
| 10 | `wx.chooseAddress` 权限 | 审核被拒 | 按微信要求声明用途；失败则回退自建表单 |
