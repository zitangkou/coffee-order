# Coffee OS 发布前全面复盘

> 日期：2026-08-29
> 范围：微信小程序顾客端、商家 Web 后台、Node/Prisma 后端、MySQL、Docker/Nginx、备份与发布门禁。
> 结论：主业务骨架和支付退款代码闭环已经具备，但还不建议直接进入正式营业。先完成下列 P0，再进行真实资质联调和提审。

## 一、P0：正式营业前必须完成

### 1. 下单与支付可恢复、可防重复

**现状**

- 确认订单页没有提交锁；用户连续点击或网络重试可能创建多笔未支付订单。
- 创建订单接口没有客户端幂等键或数据库唯一约束。
- 支付取消/失败后会跳到订单列表，但未支付订单详情没有“继续支付”和“取消订单”入口。

**完善方案**

- 前端增加提交锁和明确加载态；服务端增加 `clientRequestId`，按“用户 + 幂等键”唯一。
- 未支付详情增加继续支付、刷新支付结果、取消订单；取消仍必须先完成微信关单。
- 覆盖双击、请求超时后重试、支付取消、支付结果未知、重复拉起收银台的自动化测试。

### 2. 重构取餐码生成

**现状**

- 取餐码仅为 `S100–S999`；生成时查询全部历史订单，约 900 单后候选空间耗尽。
- 数据库没有取餐码唯一约束，并发下单和兜底随机值可能产生相同取餐码。

**完善方案**

- 改为“营业日 + 当日递增序号”，展示可保持 3–4 位，数据库保存营业日并建立唯一约束。
- 明确跨日重置规则，并覆盖并发生成、跨日切换和高峰批量下单测试。

### 3. 管理员令牌实时失效

**现状**

- 管理员中间件只相信 JWT 内的角色，不查询账号当前状态。
- 管理员被禁用、降权或重置密码后，旧令牌在两天有效期内仍可继续使用。
- `mustChangePassword` 只由前端跳转约束，可直接调用其他后台接口绕过。

**完善方案**

- 为管理员增加令牌版本；鉴权时校验账号状态、当前角色和令牌版本。
- 禁用、改角色、重置密码、主动退出时让旧令牌立即失效。
- 服务端强制首次改密账号只能访问改密接口。

### 4. 生产短信与游客接口 fail-closed

**现状**

- Compose 没有传入短信服务配置，生产环境会落到 console 模式，接口还会直接返回测试验证码。
- 验证码使用 `Math.random()`、明文存储，缺少按手机号的连续输错限制。
- H5 已暂缓，但生产 API 仍开放游客账号创建接口。

**完善方案**

- 生产启动时禁止 console 短信；未接短信供应商时关闭手机号绑定入口。
- 使用密码学安全随机数、验证码摘要、单手机号/账号错误次数限制与过期清理。
- 生产默认关闭游客登录，仅在显式开发开关下启用。

### 5. 微信小程序提审配置与订阅交互

**现状**

- `manifest.json` 仍为 `urlCheck: false`，最终提审门禁没有检查该项。
- 隐私政策和用户协议仍显示“正式提审前请补充”的草稿提示。
- 订阅消息授权在支付结果页 `onLoad` 自动调用；页面加载不属于可靠的用户点击触发场景。

**完善方案**

- 正式构建启用 URL 校验，最终门禁同时校验有效 AppID、URL 校验、HTTPS API/图片域名和订阅模板。
- 补齐经营主体、客服、留存期限、退款规则与争议处理文本，并删除所有草稿提示。
- 将订阅授权改为支付结果页明确按钮，由用户点击直接触发；记录接受、拒绝和系统禁用状态。

微信订阅消息接口要求在用户点击行为或发起支付回调后调用，参考[微信小程序订阅消息接口](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/subscribe-message/wx.requestSubscribeMessage.html)。隐私相关接口必须与平台隐私保护指引声明一致，可参考[腾讯云整理的微信隐私保护指引适配说明](https://cloud.tencent.cn/document/product/1301/97930)。

### 6. 微信支付身份校验与账务约束

**现状**

- 回调已经验签、解密、校验订单号与金额，但尚未校验回调中的商户号、AppID 和币种是否与本应用一致。
- 数据库没有约束“一笔订单只能有一条成功支付”；防御性对账能力仍不足。
- 微信 API 响应依赖 TLS，但没有校验应答签名；平台证书仍依赖人工轮换。

**完善方案**

- 校验商户号、AppID、币种和支付场景；增加订单成功支付约束或原子保护。
- 实现平台证书自动下载/轮换与微信应答验签，至少完成一次证书轮换演练。
- 增加每日支付/退款对账任务及差异告警。关单、退款及退款回调继续按微信官方接口规范验证。

参考：[关闭订单](https://pay.wechatpay.cn/doc/v3/merchant/4012791839)、[申请退款](https://pay.wechatpay.cn/doc/v3/merchant/4013071036)、[退款结果回调](https://pay.wechatpay.cn/doc/v3/merchant/4012791906)。

### 7. 明确出单方式并补齐真实支付后的出单

**现状**

- 打印服务仍是日志占位实现，启用后会把完整订单对象写入日志，可能包含顾客信息。
- 模拟支付会调用打印，真实微信支付回调成功后不会触发打印。

**完善方案**

- 若首发依赖云打印：确定型号，接入供应商 API，日志只记录订单号/结果，增加重试、去重、失败告警和后台补打。
- 若首发只看屏接单：明确打印非阻断项，并增加新订单声音提示与醒目标识。

### 8. 备份必须覆盖上传图片

**现状**

- 数据库已有备份和临时库恢复验证，但商品图、小程序码位于独立 Docker volume，不在备份范围内。
- 本机备份同步异机仍是人工待办。

**完善方案**

- 备份数据库和上传 volume，并自动同步腾讯云 COS；校验数据库、图片数量与哈希。
- 做一次整机丢失场景的异机恢复演练，而不仅是同机临时库恢复。

### 9. 固定中国营业时区

**现状**

- 容器未显式配置营业时区；统计边界和取餐码时间使用 Node 进程本地时区。
- “今日/本周/小时分布”在 UTC 环境可能整体偏移 8 小时；小时分布还使用创建时间而不是支付时间。

**完善方案**

- 配置统一业务时区并用显式时区函数计算日/周/月边界。
- 统计按支付成功时间计算，分别展示销售额、成功退款额和净收入。
- 增加北京时间跨日、月初、周一和夏令时无关性测试。

### 10. 生产默认配置必须拒绝弱密码

**现状**

- JWT 弱密钥会阻止后端启动，但 MySQL Compose 仍带弱默认密码。
- 生产容器以 root 运行，包含开发依赖、TypeScript 和 `tsx`，攻击面偏大。

**完善方案**

- 部署脚本在启动前仅检查“强配置是否已设置”，不输出配置值；缺失时立即退出。
- 后端改为多阶段构建，运行编译后 JS、只保留生产依赖，并使用非 root 用户。
- 增加 `no-new-privileges`、能力裁剪、只读根文件系统（上传目录单独可写）和镜像版本固定。

## 二、P1：上线首周前完成

1. **统一登录失效处理**：顾客令牌过期后自动清理并重新微信登录；后台 401 自动回登录页，避免持续报错。
2. **错误与日志脱敏**：500 响应不回传内部错误；结构化日志加入请求 ID，禁止打印手机号、订单完整对象和外部响应敏感字段。
3. **监控告警**：健康检查之外增加 5xx、登录失败、支付/退款回调失败、对账差异、磁盘、内存、证书到期和备份失败告警。
4. **依赖升级**：本次审计后端生产依赖为 0 个漏洞；前端依赖树为 32 个（11 高、10 中、11 低），主要来自 uni-app 构建链、旧 `vue-i18n`、`ws`、`adm-zip` 等。禁止直接 `audit fix --force`，应升级 uni-app 整套版本并做真机回归。
5. **上传安全**：校验图片真实文件头并转码，使用随机文件名，限制尺寸；替换/删除商品时清理孤儿文件。
6. **列表分页与搜索**：顾客历史订单、退款列表、商品与审计日志统一分页；后台增加订单号/取餐码/桌号搜索。
7. **退款规则**：配置可退款时限，完成订单超过时限需人工售后；失败退款提供明确重试/人工处理记录。
8. **营业时间**：从展示字符串升级为结构化营业时段，服务端自动控制接单，并保留临时停业开关。
9. **持续集成**：新增 GitHub Actions 或等价 CI，执行类型检查、构建、后端测试、migration 校验、依赖审计和小程序产物门禁。
10. **容灾发布**：应用镜像带版本号；部署前自动备份；健康失败自动停止切换；形成可执行的应用回滚和数据库向前修复流程。

## 三、P2：稳定营业后再评估

- 后台实时订单推送、声音提醒、超时变色和批量出餐；当前 10 秒轮询可先支撑单店低并发。
- 原料库存、配方扣减、售罄预警和损耗统计。
- 优惠券、积分、储值、裂变活动；储值涉及资金与合规，继续暂缓。
- 部分退款、换货/补做、售后工单与顾客沟通记录。
- 自动热销、复购分析、会员分层和经营预测；待积累真实数据后再做。
- 顾客 H5 继续暂缓，避免引入第二套登录和支付场景。

## 四、建议实施顺序

1. **安全与正确性批次**：取餐码、下单幂等、管理员令牌、短信/游客 fail-closed、时区、弱默认配置。
2. **支付体验批次**：未支付订单继续支付/取消、回调身份校验、真实支付出单、订阅按钮。
3. **提审合规批次**：URL 校验、隐私/协议最终文本、后台隐私指引、真机 UAT。
4. **运维批次**：上传文件异机备份、监控告警、容器加固、CI、版本化发布与恢复演练。
5. **营业效率批次**：云打印或新订单提醒、搜索分页、结构化营业时间和退款规则。

完成前四批并通过真实微信全链路 UAT 后，再冻结提审版本。
